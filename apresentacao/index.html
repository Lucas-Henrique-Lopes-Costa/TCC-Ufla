A pesquisa agrícola gera muito dado.

Módulo 01 · Autenticação

O ponto de entrada de todos os usuários

  • Tela construída seguindo a identidade visual da empresa cliente
  • Campos de e-mail e senha, com recuperação de senha
  • Após o login, a API devolve um par de tokens JWT: access token e refresh token
  • A sessão é persistida no armazenamento local, mantendo o usuário conectado entre acessos
Tela de login da plataforma
Módulo 01 · Autenticação

Do token à sessão: Zustand, Immer e jwt-decode

  • O store é criado com persist, que salva o conteúdo em armazenamento local sob o nome UserData
  • produce, do Immer, expõe um rascunho mutável do estado e permite escrever as alterações de forma direta
  • O access token é decodificado e nome, identificador, e-mail e perfil são extraídos das suas claims
  • O perfil extraído aqui é o que governa todo o controle de acesso da aplicação
export const loginStorePersist = create( persist((set, get) => ({ // ...estado inicial omitido setLoginInfo: ({ data }) => set(produce((draft) => { draft.isAuthenticated = true; draft.session = { accessToken: data.data.accessToken, refreshToken: data.data.refreshToken, }; const decoded = jwtDecode(data.data.accessToken); draft.userData = { name: decoded.unique_name, id: decoded.nameid, email: decoded.email, roleId: decoded.role, }; })), }), { name: "UserData" }) );
Módulo 01 · Autenticação

Renovação de sessão transparente para o usuário

  • Todas as chamadas passam por uma função de serviço que anexa o token ao cabeçalho de autorização, sem repetir essa lógica em cada requisição
  • Um interceptador de resposta age apenas quando o código é 401 e a requisição ainda não foi reexecutada
  • Nesse caso, o refresh token é usado para obter um novo access token e a requisição original é reenviada
  • O usuário não vê nada: não há logout inesperado no meio do preenchimento de um protocolo
axiosInstance.interceptors.response.use( (response) => response, async (error) => { const originalRequest = error.config; const status = error.response?.status; if (status === 401 && !originalRequest._retry) { const { refreshToken } = loginStorePersist.getState().session; originalRequest._retry = true; const response = await axiosInstance.post( "/user/refreshToken", { refreshToken } ); const newToken = response.data.data.accessToken; loginStorePersist.getState() .setLoginInfo({ data: response.data }); originalRequest.headers["Authorization"] = `Bearer ${newToken}`; return axiosInstance(originalRequest); } return Promise.reject(error); } );

Módulo 02 · Registros Agrícolas

Uma estrutura que muda de forma

  • O número de colunas da tabela varia conforme o número de repetições configurado na aba Informações
  • Novas linhas podem ser adicionadas conforme a necessidade da avaliação
  • Alguns campos são fórmulas, expressões calculadas a partir de outros campos, avaliadas em tempo de execução com mathjs
  • Cada momento de avaliação aceita fotografias de campo vinculadas ao registro
Módulo 02 · Registros Agrícolas

Todas as fotos de uma avaliação em um único arquivo

  • O problema: baixar dezenas de fotografias uma a uma inviabilizava o trabalho posterior do pesquisador
  • As imagens são buscadas na API por uma mutation do React Query e convertidas em blobs
  • As promessas são aguardadas em paralelo com Promise.all
  • O JSZip agrupa tudo em memória e o arquivo .zip é entregue ao usuário
const handleDownloadImages = async (evaluation) => { getImages(evaluation.id, { onSuccess: async ({ data }) => { const images = data.data; const blobs = await Promise.all( images.map((img) => fetch(img.url).then((res) => res.blob()) ) ); const zip = new JSZip(); blobs.forEach((blob, i) => zip.file(`${images[i].title}.jpg`, blob) ); const zipFile = await zip.generateAsync({ type: "blob", }); saveFile(zipFile, evaluation.name); }, }); };
Módulo 02 · Registros Agrícolas

Traduzir a regra do agrônomo em esquema de validação

  • A maior dificuldade do módulo foi traduzir as regras do cliente para a lógica do formulário, exigindo validação contínua a cada Sprint
  • Campos numéricos combinam required com nullable: podem ficar nulos durante o preenchimento parcial, mas são exigidos no envio
  • array().min(1) garante ao menos uma classe selecionada
  • A mensagem de cada regra é o texto exibido ao usuário quando ela é violada
const validationSchema = Yup.object().shape({ isRET: Yup.bool().required("O campo e obrigatorio"), code: Yup.string().required("O campo e obrigatorio"), culture: Yup.string(), experimentalDesign: Yup.string().nullable(), numberOfTreatments: Yup.number() .required("O campo e obrigatorio").nullable(), numberOfRepeats: Yup.number() .required("O campo e obrigatorio").nullable(), plantingDate: Yup.string().nullable(), harvestDate: Yup.string().nullable(), classes: Yup.array().min(1, "O campo e obrigatorio"), clientId: Yup.string().required("O campo e obrigatorio"), });

Módulo 03 · O desafio técnico

Muitos gráficos na mesma tela custam caro

SINTOMA

Lentidão perceptível

A renderização simultânea de múltiplos gráficos com grandes conjuntos de dados travava a interface.

CAUSA

Tudo renderizado de uma vez

Gráficos fora da área visível eram montados junto com os que o usuário estava efetivamente olhando.

SOLUÇÃO

Carregamento sob demanda

Com lazy loading, os gráficos passaram a ser renderizados apenas quando o usuário navega até a seção correspondente.

Avaliação do produto

O objetivo central foi atendido no plano técnico

Substituir o registro descentralizado em planilhas por uma plataforma própria, com acesso controlado e análise automatizada.

ENTREGA 01

Centralização

O cadastro completo dos protocolos, com formulários extensos, validação declarativa e estruturas dinâmicas para as avaliações de campo.

ENTREGA 02

Controle de acesso

Cada colaborador interage apenas com as funcionalidades do seu papel, com restrição no nível das rotas e renovação transparente de sessão.

ENTREGA 03

Análise automatizada

Gráficos e dashboards gerados a partir dos dados consolidados e exportáveis como imagens padronizadas pela identidade visual da empresa.

O que é preciso dizer com honestidade

Dificuldades, limitação e trabalhos futuros

DIFICULDADES SUPERADAS

Regras de negócio e performance

  • Traduzir o domínio agronômico para a lógica dos formulários, com validação contínua junto ao cliente
  • Manter desempenho adequado na renderização de múltiplos gráficos, mitigada com carregamento sob demanda
LIMITAÇÃO OBSERVADA

Adoção inicial reduzida

  • A adoção pelo cliente foi inicialmente baixa
  • Isso é atribuível à mudança de cultura exigida pela transição das planilhas para um sistema estruturado, e não a uma deficiência técnica da solução
TRABALHOS FUTUROS

O que viria em seguida

  • Acompanhar a adoção ao longo do tempo
  • Realizar testes de usabilidade com os colaboradores
  • Evoluir os dashboards com novos tipos de análise

A área de visualização de dados passou a orientar os interesses profissionais, integrando construção de aplicações web com análise de informação.

O caminho inverso

O que a graduação deu, e o que faltou

DISCIPLINAS QUE SUSTENTARAM O TRABALHO
  • Engenharia de Software: ciclo de desenvolvimento, requisitos e métodos ágeis
  • Programação Orientada a Objetos: modularidade e responsabilidade única traduzidas na componentização do React
  • Banco de Dados: entender as estruturas devolvidas pela API
  • Interação Humano-Computador: decisões de usabilidade e organização das telas
  • Algoritmos e Estruturas de Dados: manipulação de vetores e estruturas aninhadas
LACUNAS PERCEBIDAS
  • Frameworks modernos de front-end, como React e o ecossistema em torno do TypeScript, vistos de forma superficial nas obrigatórias
  • Testes automatizados de interface, pouco trabalhados no curso e cada vez mais valorizados no mercado
  • Integração contínua, versionamento em equipe (com pull requests e revisão de código) e deploy em nuvem

Cobrir essas lacunas teria reduzido a curva de aprendizado dos primeiros dias de estágio.
